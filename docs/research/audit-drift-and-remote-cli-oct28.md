#### 3.1. First-Principles & Flow Analysis of Per-Client Revocation (`think.B1–B5`, `flow.B1–B6`, `proportion.A1–B3`)
- **Goal Chain (`think.B1`):** Owner spots an unwanted, stale, or unrecognized client in Section 7 (`Clients`) → revokes that specific client's current and future access immediately from that row → without signing out other healthy OAuth connectors (`claude.ai`, `ChatGPT`, `Grok`, `Gemini`, `Notion`) and without hunting across Section 7 and Section 1.
- **Facts vs Assumptions (`think.B2`):**
  1. **Fact 1 (Architecture invariant):** AkiMCP uses **one shared access token** plus **per-client refresh tokens** (`docs/plan/done/single-access-token.md`). Therefore, dropping client X's refresh token (`removeClient(clientId)`) **combined with** a soft access-token roll (`rotateAccessToken({ revokeRefresh: false })`) immediately invalidates client X's access token (`bearerStatus` → `'retired'` → HTTP `401`) while **every other signed-in OAuth client retains its refresh token and silently refreshes** to the new shared access token on its next request!
  2. **Fact 2 (Three distinct client states in `listClients()`, `scripts/oauth.js:186-201`):**
     - **State 1 — `pending` (`kind === 'dcr' && !approvedAt`):** Registered via `/register`, never approved with passphrase, holds **zero tokens** (`tokenAt: null`, `signedIn: false`). Removing it only needs to delete the DCR entry — no token roll is ever needed.
     - **State 2 — `signedIn: false` but previously approved (`approvedAt !== null`):** Holds no refresh token, so it cannot renew, but may still hold the current shared access token if `tokenAt` was after the last roll.
     - **State 3 — `signedIn: true`:** Holds both a refresh token and the current shared access token.
  3. **False Assumption in Current UI (`flow.B5`):** Assuming that because the access token is shared, Section 7 can only drop the refresh token and must hand off the access-token roll to the human as homework in Section 1 (`coding.B3` / `flow.B4` manual coordination smell).
- **Native-Flow Redesign (`flow.B6`, `ux.A4`, `ux.A5`):**
  1. **For `pending` rows (`!approvedAt`):** Show a single `Delete` button that calls `POST /api/clients/remove` (`{ clientId, roll: false }`) with no scary token-roll warning — 1 click removes the unapproved registration.
  2. **For approved / signed-in rows (`approvedAt || signedIn`):**
     - Make the primary row action **`Revoke`** (or `Sign out & roll` for the `static` client), which sends `POST /api/clients/remove` with `{ clientId, roll: true }`. On the server (`scripts/panel.js` + `scripts/oauth.js`), `removeClient(clientId)` drops the client's refresh token (and DCR record) **and**, when `roll: true`, immediately calls `rotateAccessToken({ revokeRefresh: false })` in the same request, returning the updated state (or reloading keeping scroll/section so Section 1 snippets also reflect the fresh token).
     - Provide a secondary lightweight action (`Forget` / `Remove only` with `roll: false`) for when the owner wants to clean up an old record without rolling the shared token (e.g., when removing several rows in a batch before rolling once, or when the token was already rolled earlier).
- **Critique (`think.B3`):**
  - *Steelman keeping the manual 2-step split:* If an owner removes 3 old connectors in a row, rolling on each click would soft-roll the shared token 3 times instead of once, and local Bearer-snippet clients (`Claude Code`, `Codex`, `Cursor`) need one Re-apply after a roll.
  - *Attack & Synthesis:* The 90% case when clicking revoke on a live client is evicting that client *now*; forcing a Section 7 → Section 1 scroll on every single revoke optimizes for the rare multi-delete batch at the expense of the primary security action (`ux.A4`). Offering **`Revoke` (rolls token now)** as primary alongside **`Remove only` (no roll)** (or a checkbox/choice in the confirm dialog, or a batch `"Remove & roll"` button) satisfies both the single-eviction case and the batch-cleanup case with zero cross-section scrolling!

#### 3.2. Ecosystem Table Standard Applied to Panel Tables (`F10` — `ui.A1`, `ux.A1–A5`)
Adapting the ecosystem's table rules (`AdminToolbar` + `AdminColumn` + `useTableSort` comparator) to the zero-dependency vanilla JS control panel (`public/panel-client.js`, `public/panel.css`):
1. **Single Toolbar per Table (`AdminToolbar` rule):**
   - Place one `.table-toolbar` row directly above `#clientsList` and one above `#callersList` containing all controls for that table in one place (`ux.A5` motor cost & `ux.A2` recognition):
     - **`Clients` toolbar:** search input (`placeholder="filter by name, redirect host, IP, agent…"`), status filter select (`All statuses` · `Signed in` · `Pending approval` · `Signed out`), visible count note (`"Showing X of Y clients"` — explicitly stating when a filter/sort is active on loaded rows), and a **`Refresh`** button right in the toolbar.
     - **`Active now` toolbar:** search input (`placeholder="filter by caller IP or User-Agent…"`), visible count note (`"Showing X of Y callers"`), and a **`Refresh`** button.
2. **Opt-Out Column Sorting with Raw-Value Comparator (`useTableSort` rule):**
   - **Opt-out sort:** Every column in `renderTable(containerId, columns, rows, emptyText, rowClass, opts)` is sortable by default unless `sortable: false` is set on the column (action columns like `Remove`/`Revoke` and `Switch` set `sortable: false`).
   - **No client `defaultSortKey` / `defaultSortDir`:** On initial load, rows stay in the server's authoritative order (`listClients()` in `scripts/oauth.js:211` sorts by `lastActivityAt` desc; `listCallers()` sorts by `lastSeen` desc). Clicking a sortable `<th>` cycles `asc → desc → server-default`, indicated by FontAwesome icons (`fa-sort`, `fa-sort-up`, `fa-sort-down`).
   - **Comparator contract (`compareTableValues`):**
     1. **Nil sinks to the bottom in BOTH `asc` and `desc`:** `null`, `undefined`, `''`, `'—'`, `0` (for missing timestamps) always sort after non-nil values regardless of sort direction, so "never approved" or "before tracking" rows never jump to the top when sorting ascending (`think.B5` EC).
     2. **Raw `sortValue` separation:** Columns that render DOM nodes or relative time strings (`timeCell(c.tokenAt)` → `"3 h ago"`) declare `sortValue: (row) => row.tokenAt` (numeric epoch ms) or `sortValue: (row) => row.requests` (number), so sorting compares numbers/timestamps rather than formatted strings.
     3. **Fallback chain:** numbers → numeric strings → case-insensitive `localeCompare(undefined, { numeric: true, sensitivity: 'base' })`.
3. **RWD & Styling (`ui.A1` subtraction-first):**
   - Keep horizontal scroll (`.tablewrap { overflow-x: auto }`), never collapse table rows into cards on mobile, and **never sticky-pin any column** (so mobile horizontal scrolling stays unobstructed).
   - Style `.table-toolbar` and sortable `th[data-sort]` using only existing CSS variables in `public/panel.css` (`--bg`, `--card`, `--line`, `--fg`, `--muted`, `--accent`).
